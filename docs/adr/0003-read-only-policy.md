# ADR-0003: Read-only политика и запрет destructive-команд

**Статус:** Accepted
**Дата:** 2026-11-05
**Контекст:** SPEC §5, RULES §7, SECURITY.md §2

## Контекст

Инструмент анализирует рабочие копии разработчика, где могут быть
незакоммиченные изменения. Автоматический `git pull`, `git merge` или
`git reset --hard` может привести к потере работы. При этом пользователь
ожидает, что инструмент «поможет» синхронизировать репозитории.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Полная автоматизация pull/push | Удобно | Риск потери данных, недоверие |
| B. Read-only + рекомендации | Безопасно | Меньше «магии», нужны точные команды |
| C. Read-only по умолчанию + явные мутации с подтверждением (v0.2) | Баланс | Сложнее UI |

## Решение

**Вариант B для v0.1.0, с планом на C в v0.2.0.**

- `git fetch` разрешён: обновляет только `refs/remotes/*`, не трогает
  рабочую директорию.
- `pull`, `push`, `merge`, `reset`, `clean`, `checkout .` — **не выполняются**
  ни при каких условиях в v0.1.0.
- В UI — только текст рекомендаций и готовые команды для копирования.

Мутации появятся как `POST /repositories/{id}/actions/{action}` с
`confirm=true` и аудитом.

## Последствия

- Пользователь не теряет данные из-за автоматики.
- Инструмент менее «удобен», но безопасен; это осознанный trade-off.
- Рекомендации должны быть точными, иначе пользователь скопирует неверную
  команду.
