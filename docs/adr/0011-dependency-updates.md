# ADR-0011: Explicit, preflight-checked dependency updates

**Статус:** Accepted
**Дата:** 2026-11-06
**Контекст:** Sprint 34 (S34-001…S34-005), SPEC §3.20, ARCHITECTURE §17

## Контекст

Пользователю нужен способ обновить зависимости проекта из дашборда. Команды
`pip install --upgrade` и `pnpm/npm update` меняют окружение и/или lock-файлы,
могут конфликтовать с незакоммиченными изменениями и ломать сборку. По умолчанию
система обязана оставаться read-only.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Полностью ручное обновление вне приложения | Безопасно | Нет UX-интеграции, нет аудита |
| B. Автообновление по расписанию | Удобно | Нарушает read-only, риск сломать окружение |
| C. Явное подтверждение + preflight + audit | Контроль, предсказуемость | Ограниченный набор команд |

## Решение

**Вариант C.**

- Обновление выполняется только при `confirm=true` и только для выбранного
  ecosystem (`python`/`node`).
- Preflight проверяет `git status --porcelain`; любой вывод → `409` с
  `Worktree must be clean`. Отказ и ошибка пишутся в `action_log`
  (`action="update-dependencies"`).
- Python: `pip install -r requirements.txt --upgrade` (через текущий
  интерпретатор). Node: `pnpm update` при `pnpm-lock.yaml`, иначе `npm update`.
- Timeout 180 с, вывод ≤ 10 000 символов, credentials в URL редактируются.
- Bulk-режим — concurrency 2, `actor=bulk`; один упавший репозиторий не
  отменяет остальные.
- Автоматического коммита/отката нет; пользователь проверяет diff сам.
- Вне этого действия `pip`/`pnpm`/`npm` не запускаются.

## Последствия

- Пользователь должен закоммитить/застейджить изменения перед обновлением.
- `pip` меняет окружение backend, `pnpm/npm` могут изменить lock-файлы —
  это явно предупреждается в UI (KI-014).
- Нет выборочного обновления пакетов и флагов `--force`/`--legacy-peer-deps`.
- Долгие операции ограничены таймаутом; результат доступен в `ActionLog`.
