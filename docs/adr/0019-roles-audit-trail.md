# ADR-0019: Roles and audit trail

**Статус:** Accepted
**Дата:** 2026-11-11
**Контекст:** Спринт 58 (S58-001..S58-004), v1.3.0

## Контекст

Приложение выросло из single-user режима: один `admin` мог всё, включая push,
обновление зависимостей и изменение настроек. Для командного использования
нужен наблюдатель, который видит состояние проектов, но не может выполнять
мутации, и журнал того, кто и что сделал. При этом локальный режим
`AUTH_ENABLED=false` должен оставаться простым.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Оставить только admin | Нет кода | Нет read-only наблюдателя и аудита |
| Полный RBAC (роли + права на репозитории) | Гибко | Избыточно для v1.3.0 |
| Две роли `admin`/`auditor` + действие-ориентированный `require_admin` | Просто, покрывает сценарий | Нет гранулярных прав на отдельные репозитории |
| Роль только в JWT | Быстро | Устаревает при смене роли, нельзя доверять токену |

## Решение

- В `users` добавлено поле `role` (`admin`/`auditor`, default `auditor`).
  Bootstrap-пользователь создаётся как `admin`; миграция 013 переводит
  существующего единственного пользователя в `admin`.
- Роль читается из БД на каждом запросе; claim `role` в JWT информационный.
  Зависимость `require_admin` возвращает `403 insufficient_role` для auditor.
- `AUTH_ENABLED=false` — неявный локальный admin (обратная совместимость).
- Защита от lockout: нельзя понизить/отключить себя или последнего активного
  admin.
- `audit_log` — append-only таблица (`user_id`, `action`, `entity_type`,
  `entity_id`, `details`, `created_at`). `AuditService.log()` вызывается после
  успешных мутаций; `details` санитизируются и ограничены 4000 символами.
- API `GET /api/v1/audit` и `/api/v1/users` доступны только admin.

## Последствия

- Auditor безопасно смотрит дашборд, зависимости, CVE, AI-отчёты и поиск, но
  не запускает scan, не меняет настройки и не выполняет actions.
- Появляется неизменяемый журнал security-relevant действий; `action_log`
  остаётся журналом вывода команд.
- Нет гранулярных прав на отдельные репозитории и retention-политики —
  кандидаты следующих версий.
- Ошибка записи аудита не откатывает уже выполненную мутацию; при требовании
  строгого fail-closed нужна транзакционная связка аудита и действия.
