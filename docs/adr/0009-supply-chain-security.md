# ADR-0009: OSV.dev and regex secret scanning without package-manager execution

**Статус:** Accepted
**Дата:** 2026-11-06
**Контекст:** Sprint 28 (S28-001…S28-006), SPEC §3.16, ARCHITECTURE §12

## Контекст

Нужно показывать уязвимости (CVE) в объявленных зависимостях и потенциальные
секреты в рабочей директории локальных репозиториев. Ограничения проекта:
read-only, никаких установок/обновлений пакетов, никаких новых зависимостей без
ADR, локальный API должен отвечать без 5xx даже при недоступности внешнего
сервиса.

Рассматривались два независимых вопроса: источник advisories и способ поиска
секретов.

## Рассмотренные варианты

### CVE

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Локальная база advisories (OSV database export) | Нет сети, полный контроль | Большой объём, нужна синхронизация и миграции |
| B. `pip-audit` / `npm audit` | Знакомая семантика | Запускает пакетные менеджеры, требует lock-файлов/установки, меняет поведение |
| C. OSV.dev API (`/v1/querybatch`) + TTL-кэш | Бесплатно, единый формат для PyPI/npm, batch, без установки | Нет SLA, rate-limit, нужен кэш и деградация |

### Secret scanning

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. gitleaks/trufflehog как зависимость | Готовые правила, история Git | Новая зависимость, тяжёлый скан истории, сложная интеграция |
| B. Фиксированный regex-набор в stdlib `re` | Без зависимостей, быстро, предсказуемо, тестируемо | Ложные срабатывания, нет entropy/истории |
| C. Полный SAST | Глубокий анализ | Несоразмерно задаче, тяжёлая зависимость |

## Решение

**CVE — вариант C, секреты — вариант B.**

- `OsvClient` вызывает `POST https://api.osv.dev/v1/querybatch` батчами по 100
  запросов. Ecosystem: `PyPI` / `npm`. Отдельный `/v1/query` не используется.
- Версия: для `exact` передаётся точная версия (`version_source=exact`), для
  диапазона — нижняя граница (`version_source=lower_bound`). Если версию
  извлечь нельзя, пакет попадает в `unknown_packages` и не считается
  проверенным: отсутствие данных не равно отсутствию уязвимостей.
- Severity: CVSS v3 base score вычисляется из вектора (`severity[].score`);
  при отсутствии — `database_specific.severity`; иначе `unknown`. Порог
  `min_severity` по умолчанию `high`, но `summary` всегда считается по полному
  набору.
- Кэш `security_cache` (ключ `osv:<ecosystem>:<package>:<version>`) с TTL 6 ч,
  включая negative cache. `refresh=true` обходит TTL.
- Ошибки OSV (`rate_limited`, `timeout`, `osv_unavailable`) не дают 5xx:
  используется stale-кэш, иначе `ecosystem.status=unavailable`.
- Secret Scanner читает только рабочую директорию: `git ls-files -z -co
  --exclude-standard`, а вне Git — `os.walk` с исключениями. История Git не
  сканируется.
- Правила фиксированы в коде (AWS Access Key/Secret, GitHub token, JWT, private
  key); полное значение маскируется (`ghp_****1234`) и не попадает в логи,
  ответы или БД.
- Лимиты: 5000 файлов, 1 MiB на файл, бинарные файлы пропускаются. Строка с
  `# iiruchating:ignore-secret` подавляет ложное срабатывание.
- Новые зависимости не добавляются: `httpx` уже используется, regex — stdlib.

## Последствия

- Проверка не запускает `pip`/`npm`/`pnpm` и не меняет рабочую директорию.
- OSV.dev не даёт SLA: возможны partial-отчёты и задержки (KI-011).
- Regex-сканер даёт ложные срабатывания на фикстурах/примерах (KI-012);
  энтропийные эвристики и пользовательские правила — кандидаты в v0.7+.
- Полная история Git, SBOM, лицензионный аудит и транзитивные зависимости —
  вне scope v0.6.0.
