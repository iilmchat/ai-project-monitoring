# ADR-0013: E2E-тестирование через Playwright с моками API

**Статус:** Accepted
**Дата:** 2026-11-08
**Контекст:** Спринт 42 (S42-001), v0.9.0 «Search & Reliability»

## Контекст

Нужно защитить три критических пользовательских пути: onboarding → сканирование →
дашборд, переключение языка/темы и генерацию AI-коммита. Vitest + Testing Library
проверяют компоненты в jsdom, но не покрывают реальный браузерный рендеринг,
навигацию React Router и сетевые запросы.

При этом реальный backend требует локальную БД, 34 репозитория и запущенную LLM.
Такая инфраструктура делает E2E медленными, недетерминированными и опасными:
тесты могли бы сканировать реальные проекты пользователя.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Playwright + `page.route()` | Быстрый, детерминированный, не требует backend/LLM, поддерживает trace/video | Моки нужно поддерживать в актуальном состоянии |
| Playwright + MSW | Переиспользование хендлеров, близко к реальному fetch | Ещё одна зависимость и слой конфигурации |
| Playwright + реальный backend и tmp-репозитории | Максимальная достоверность | Медленно, сложная изоляция БД, риск задеть реальные проекты |
| Cypress | Зрелая экосистема | Тяжелее, хуже параллелизация и поддержка в текущем стеке |

## Решение

Используем `@playwright/test` с одним catch-all обработчиком
`page.route('**/api/v1/**')` в `frontend/e2e/mock-api.ts`. Тесты запускаются
против Vite dev-сервера (`http://localhost:5173`), браузер — Chromium, локаль —
`ru-RU`, чтобы стартовый язык был предсказуем. Мок-состояние изменяемое: `POST
/scan` добавляет репозиторий в ответ `/dashboard`, поэтому сценарий onboarding
проверяет полный цикл без реального сканирования.

Мок-LLM реализован тем же `page.route()`: `POST
/repositories/{id}/ai/commit-message` возвращает детерминированное сообщение.

## Последствия

- E2E не ходят в сеть, не трогают реальные репозитории и не требуют backend/LLM.
- При изменении контрактов API мок-файл нужно обновлять вместе с `client.ts`.
- Для проверки интеграции с настоящим backend остаются backend-тесты на
  tmp-репозиториях; E2E сознательно проверяют UI-поведение.
- При появлении аутентификации (v0.9.0+) сценарий onboarding потребует
  пересмотра.
