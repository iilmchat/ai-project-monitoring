## KI-001 · Accepted · Med · git/fetch · Нет таймаута на fetch для больших репозиториев

**Описание:** `git fetch` на очень больших репозиториях (monorepo, >1 ГБ) может занимать минуты; таймаут 30 с может быть недостаточным, а прерывание fetch оставляет `.git/FETCH_HEAD` в неконсистентном состоянии (безопасно, но следующий fetch начнётся заново).

**Workaround:** Увеличить `FETCH_TIMEOUT` (ENV); при таймауте — `remote_status=unavailable`, повторить вручную.

**План:** Адаптивный таймаут (замер времени fetch, увеличение для больших репо); кэширование `packfile` между вызовами.

## KI-002 · Open · Low · git/pygit2 · `repo.status()` на очень больших деревьях может быть медленным

**Описание:** `pygit2.Repository.status()` обходит всю рабочую директорию; на репозиториях с сотнями тысяч файлов (например, `node_modules` внутри репо, если не в `.gitignore`) может занимать секунды. Игнорирование через `.gitignore` работает, но если файлы не игнорируются, статус будет тяжёлым.

**Workaround:** `SCAN_IGNORE` для тяжёлых директорий; кэш статуса (`STATUS_TTL_SECONDS`).

**План:** Использовать `git status --porcelain -uno` (без untracked) для быстрого «грязный/чистый», и полный статус — по запросу.

## KI-003 · Open · Med · remote · GitHub Compare API rate limit (60/час без токена)

**Описание:** Compare API GitHub без `GITHUB_TOKEN` ограничен 60 запросами/час. При большом числе репозиториев и частом обновлении лимит исчерпывается, и `compare` начинает возвращать 403.

**Workaround:** Задать `GITHUB_TOKEN` (5000/час); использовать локальный `rev-list` вместо Compare API, когда детали не нужны.

**План:** Приоритет локального сравнения; Compare API — только при явном запросе деталей; кэш результатов compare.
